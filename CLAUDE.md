# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A bilingual (English/Arabic, RTL-aware) horse-services marketplace and CMS-driven public website, built on Laravel 12 + Filament v4 (PHP ^8.2). The README is the stock Laravel one and says nothing about the project. Public pages are Blade views styled with Tailwind 4; all admin work happens in Filament panels. On top of that sits a **paid service orders** system (forms → orders → payment gateways → customer accounts → notifications → income reports), described below.

## Commands

```bash
composer dev                  # php artisan serve + queue:listen + vite, via concurrently
npm run dev / npm run build   # Vite. `public/build` is gitignored, so JS/CSS changes need a build to show up (the admin theme too: new Tailwind classes in resources/views/filament/** only exist after a build)
composer test                 # config:clear, then php artisan test
php artisan test --filter=RacingCalendarTest              # one test class
php artisan test tests/Unit/RacingParserTest.php          # one file
vendor/bin/pint <paths>       # code style (laravel/pint); pass explicit paths, the tree has uncommitted work from other people
php artisan racing:warm       # pre-warm the racing handicap cache (not scheduled; add to cron if wanted)
php artisan form-builder:move-uploads-private [--dry-run]   # move old public form uploads to the private disk
```

Scheduled in `routes/console.php` (production needs a `schedule:run` cron **and** a queue worker): `transfer-posts:expire` (00:05), `horse-sale-posts:expire` (00:10), `stables:generate-slots` (00:20), `stables:send-reminders` (hourly), `orders:expire-pending` and `orders:recover-late-payments` (every 5 min), `model:prune` for `CustomerOtp` (daily), `evolution:cleanup` (03:30, WhatsApp plugin history).

The local tree is often `php artisan optimize`d: `bootstrap/cache/` holds cached config, routes **and Filament components** (`bootstrap/cache/filament/panels/*.php`). After adding a Filament page/resource, run `php artisan optimize` again (or `route:cache` + `filament:cache-components`): with a stale component cache the new page loads, but every click on it (actions, modals, downloads) answers **419 "page expired"**, because Livewire cannot find the component by name and reports that as a 419.

`composer.json`'s `post-autoload-dump` runs `filament:upgrade`, so `composer dump-autoload` touches Filament assets.

The DB is MySQL (`hrs`); `hrse (1).sql` in the root is a dump. `.env.example` uses the `database` queue and cache drivers (a local `.env` may use `sync`); the order notifications are queued, so a worker must run wherever the driver is not `sync`. Mail defaults to `MAIL_MAILER=log`; SMTP details come from the admin "SMTP Settings" page, but the mailer itself must be `smtp` in `.env`.

After adding a resource or page, run `php artisan shield:generate --all --panel=admin --ignore-existing-policies`: Shield gates everything with `ViewAny:Model`-style permissions and only super-admins see a screen until they exist. Each new resource here has a policy following that pattern. Without `--ignore-existing-policies` Shield rewrites hand-edited policies: `StablePolicy` and the stable booking policies also let stable owners in (see below), and a regenerated one silently locks them out.

### Testing gotchas

- phpunit uses in-memory sqlite, but **the migrations are MySQL-only** (`ALTER … MODIFY`), so `RefreshDatabase` fails. The stock `ExampleTest` files fail for this reason (the one known failing test). Don't reach for `RefreshDatabase`.
- Instead, tests build only the tables they need. Traits in `tests/Concerns/`: `PreparesSiteLayout` (empty `cms_menus`/`cms_redirects`, pre-warmed `site_settings.all` cache, needed by anything rendering the site layout), `FakesRacingSource` (adds captured responses from `tests/Fixtures/racing/`), `PreparesOrderSite` (runs the real, portable order/fee/commission/notification-log migrations; `seedSiteSettings([...])` fakes site settings without a `site_settings` table), `MakesOrderForms` (form-builder tables + a linked form), `PreparesCustomerSite` (customers, SMS driver and Tamimah fakes), `MakesReviewOrders` (orders through review stages, `reviewer(['role'])` stub users with a `hasRole()`, `stagedOrder()`). Pick the highest one you need. Spatie's permission tables and the users table are portable, so a test that needs real roles can `require` their migrations.
- `Http::fake()` stubs stack (the first match wins): start from `Http::swap(new Factory)` or the helper (`replaceRacingFake()`, `tamimahAnswers()`) when overriding mid-test.
- Admin pages are tested with Livewire as a plain stub `Authenticatable` plus `Gate::before(fn () => true)` and `Filament::setCurrentPanel(...)`: the real `User` model queries the (MySQL-only) permission tables on every ability check.
- `phpunit.xml` raises `memory_limit` to 512M: every test boots an app, and the racing PDF logo guard (correctly) skips big logos when memory is short.
- **Never run `php artisan test` while `bootstrap/cache/config.php` exists** (after `php artisan optimize`/`config:cache`): phpunit's sqlite env is ignored and tests hit the real MySQL. `PreparesSiteLayout` then flushes the real cache and stores an empty `site_settings.all` (the site loses its logo and settings until `cache:forget site_settings.all`). Use `composer test` (it clears config first), or `config:clear` → test → `config:cache`.
- Do not `Event::listen` anything in `app/Listeners`: Laravel auto-discovers that folder, so a manual registration runs each listener twice.

## Architecture

### Surfaces

1. **Public site** (`routes/web.php`, controllers in `app/Http/Controllers/Site/`, views in `resources/views/site/`, layout `components/layouts/site.blade.php`). Hardcoded routes for the directory/marketplace sections (stables, clinics, centers, shops, farriers, transfer-board, horses-for-sale, tools-for-sale, events, video-library, blog, racing), plus checkout (`/pay/*`, `/payment/*`), order status (`/orders/{number}`) and the customer area (`/account/*`).
2. **Admin panel** `/admin` (`AdminPanelProvider`): one Filament resource per model in `app/Filament/Resources/`, plus Shield (roles/permissions), activity log, backup/health, file explorer, API service, and the local `packstub/filament-form-builder` package (path repo in `packages/`, symlinked). Payments things live under the "Payments" navigation group.
3. **"Public" Filament panel** `/transportation` (`PublicPanelProvider`, `app/Filament/Public/`): the user-facing transfer-post board built as a Filament resource.
4. **Stable owner panel** `/stable` (`StablePanelProvider`, `app/Filament/Stable/`): stable owners run their stables here (see "Stable bookings").

### CMS-driven pages

`PageController` resolves a `CmsPage` by slug and renders its page-builder `content` JSON through `resources/views/cms/render-blocks.blade.php`. Block schemas live in `app/Filament/Blocks/Cms/CmsBlocks.php`; each block type has a matching `resources/views/cms/blocks/{type}.blade.php`. Adding a block means touching both.

Hardcoded routes (e.g. `/stables`) still take their SEO metadata from a published `CmsPage` with the same slug via `Support\Seo::forSlug()`.

The catch-all `/{slug}` route matches only **single-segment** paths, and excludes reserved prefixes with a prefix-based negative-lookahead regex. A new single-segment top-level route must be added to that regex, or `PageController` shadows it; but adding a prefix blocks every CMS slug that starts with it (`pay` would block `payment-terms`). So new sections use two-or-more segment paths (`/account/orders`, `/pay/{order}`) and stay out of the regex. The `Route::fallback` then consults `CmsRedirect` rows before 404ing.

Site-wide settings come from two places: `SiteSetting` (cached under `site_settings.all`; layout/SEO/PDF logo, gateway, SMS, VAT settings) and `Setting` via `SettingsService` (key/value, SMTP config). Credentials go through `Support\SecretSetting` (encrypted with the app key, `enc:` prefix; legacy plain values still read).

### Bilingual (EN/AR) — three coexisting patterns

- `config/languages.php` is the single source of truth for locales. `SetLocale` middleware (appended to the `web` group in `bootstrap/app.php`) reads `?lang=` then the session. The default locale is `APP_LOCALE`.
- **Simple models** (Country, Region, City, Type, Horse, Partner, SuccessStory, Service): `en_x`/`ar_x` column pairs (Service keeps `name`/`description` as the English ones and adds `ar_name`/`ar_description`; use `localizedName()`).
- **CMS models** (CmsPage/Post/Category/MenuItem, ServiceFeeSetting, CommissionSetting): `spatie/laravel-translatable` JSON columns.
- **Block content**: `{en:…, ar:…}` nested per field, read with `Support\Localized::value($data, 'key')` and built in forms with `Filament\Support\TranslatableInput::grid()`.
- UI strings live in `lang/{en,ar}/*.php`, one file per area (`admin_*.php` for admin, plain names for the public site). Add every string to both languages.
- **Filament slugs are always generated from the English field**, hardcoded (`$code === 'en'` inside a `TranslatableInput::grid`), never `TranslatableInput::defaultLocale()`. That reads `APP_LOCALE`, which differs between environments, and `Str::slug()` on Arabic gives empty or poor results.
- Anything sent to a customer (SMS, email, receipt) is rendered in the order's stored `locale`, not the viewer's; `Support\Locale::within()` switches and restores.

### Paid service orders

The flow: a form-builder form linked to a `Service` → submission becomes a `ServiceOrder` → free orders are received at once, paid ones go to a gateway → payment confirmed → `ServiceOrderReceived` → customer email/SMS (+ reviewers), and the order enters review if its form has stages → stages approved (or one rejects, which ends the request and makes a refund due) → an admin completes it → `ServiceOrderCompleted` → customer told again. The customer signs in with phone + SMS code to see orders, documents and receipts.

**Money (the rules that are easy to get wrong).** Everything is 3-decimal OMR, computed in **integer baisa** (`Services\Orders\OrderPricing` → `PriceBreakdown`); columns are `decimal(10,3)`. `total = price + fee + VAT on price + VAT on fee`. The **service fee is added on top** of the price and is our income; VAT (default 5%, settings `vat.enabled|rate`) applies to price and fee. An optional **commission** (`CommissionSetting`) comes out of the client's share (the price), never added to the customer's total. Fee and commission rules resolve form > service > global, active and in date. All of it is **snapshotted on the order** at creation (amounts and the rule behind them), so editing a rule never changes an old order. All money lands in the client's single merchant account; `IncomeStatement` works out what the client owes us: `fee + VAT on fee + earned commission`. A refund returns price + its VAT, **never the fee**, and shrinks the commission proportionally (`OrderMoney::earnedCommission`). Free services (price 0) carry no fee, VAT or commission.

**Code map.**
- `app/Services/Orders/`: `OrderPricing`, `CreateServiceOrder` (also normalizes the phone), `OrderWorkflow` (review, approve, reject, complete), `OrderRefundService`, `OrderDocumentService`, `OrderReceiptPdf`, `OrderMoney`. `Models\ServiceOrder` (+ `OrderEvent` timeline, `OrderStage`, `OrderRefund`, `OrderDocument`, `PaymentGatewayLog`).
- `app/Services/Payments/`: gateways `Thawani`/`Nbo`/`CcAvenue`/`Demo` (ported from the booking apps under `~/Downloads/booking/`), `PaymentGateways` (enabled + configured ones), and `OrderPaymentService`, **the only place payment state changes** (row lock, idempotent, receipt numbers `RC-year-000001`). `Site\PaymentController` handles checkout, returns, webhook and callbacks. Never trust a redirect: Thawani is re-fetched from Thawani; NBO/CCAvenue callbacks must match the amount. Callback routes are CSRF-exempt in `bootstrap/app.php`. Every gateway call is logged (`payment_gateway_logs`, secrets redacted; its outcome scope uses MySQL JSON functions, so it is not testable on sqlite).
- Sweeps: `orders:expire-pending` cancels unpaid orders after `config('payments.pending_ttl_minutes')` (checking Thawani first); `orders:recover-late-payments` revives ones a Thawani session was paid for later (only system-cancelled ones; an admin-cancelled order that gets paid is flagged for a manual refund).
- Forms: the form-builder fork (see below) has a "Service & payment" tab (`Filament\Support\FormPaymentTab`, values in the form's `settings.payment|customer|notifications`), read through `Support\FormOrderSettings`. `Listeners\CreateOrderFromSubmission` creates the order and redirects the visitor to `/pay/{order}` (or the order page if free). A form whose service is inactive/deleted is closed; a price notice is shown above the form.
- Customers: `Models\Customer` on the separate `customer` guard (no password, cannot reach the admin). `Services\Auth\CustomerOtpService`: 6-digit code, 5 minutes, 5 tries, single use, keyed hash only, rate limits counted from the DB. Guest orders attach when their (verified) phone signs in. Phones are always stored as digits with country code (`Support\PhoneNumber`; 8 digits = Omani).
- SMS: `Services\Sms\SmsManager` (drivers `tamimah`, `demo` = show the code on screen for presentations, `log` = dev only), configured on the admin SMS Settings page, every attempt in `notification_logs`. `TamimahSmsGateway` follows the SOAP `SendSMS` description on tamimahsms.com; what its StatusCodes mean is unknown, so success = "Proccessed >= 1" unless "success codes" are set.
- Notifications: `Listeners\NotifyOnOrderReceived|Completed` → queued `Jobs\SendOrderNotification` (one per channel, per-form toggles, never throws, deduped by the log), `SendReviewerNotification` (a priced form's reviewers are emailed when the order is **paid**, not at submission; the package hook `holdNotificationsWhen` holds the plain email). Texts are in `lang/*/notifications.php`.
- Reports: `Services\Reports\IncomeStatement` (rows by day paid, exact baisa sums; free/unpaid excluded, refunded orders included) feeds the admin `IncomeReport` page, `StatementPdf`/`StatementCsv`, and the `IncomeOverview`/`IncomeChart` dashboard widgets.
- PDFs use `Services\Pdf\MpdfFactory` (Cairo font, Arabic shaping); receipts and statements are plain-table views in `resources/views/pdf/`.

**Review, rejection, refunds, documents.** A form's "Service & payment" tab can define ordered review **stages** (a name per language + a Spatie **role**; stored in the form's `settings.approval.stages`, plus `requires_document`). When an order is received, `Listeners\StartOrderReview` copies them into `order_stages` (a snapshot: editing or deleting the form never touches an order in review) and sets it `in_review`; `SendStageReviewNotification` emails the holders of the current stage's role. Only holders of the *current* stage's role (or `super_admin`) may approve or reject, row-locked, one stage at a time; the last approval sets `processing`. A rejection needs a reason (shown to the customer), ends the request, and notifies the customer; if it was paid, a **refund is due** (`ServiceOrder::refundDue()`). Completing needs no pending stage and, if the form asks, an uploaded document (`OrderWorkflow::completionBlockers`). This is our own small workflow, not `ffhs/filament-package_ffhs_approvals` (installed, unused): that package stores no comment/reason on a decision and has no reject-then-refund concept. Refunds are **recorded** by an admin after making them at the gateway or by bank transfer (`OrderRefundService`; there is no automatic gateway refund call): at most the price + its VAT minus earlier refunds, never the fee; full refund sets `payment_status = refunded`; each refund notifies the customer. Result documents live on the private `local` disk (`order-documents/{order}/`) and are served only by `OrderDocumentController`: to their own signed-in customer, or to an admin through a signed link. Watch out: relations with a default `orderBy` (events, refunds, stages) need `->reorder()->latest('id')` to get the newest row; plain `latest('id')` still sorts ascending first.

**Notification texts are admin-editable** (Settings → Notification Texts): customer-facing SMS and email texts are read through `Support\NotificationText::get('sms.completed', [...])` (an override saved in the `notifications.texts` site setting, else `lang/*/notifications.php`). Never call `__('notifications.…')` for those keys; only the two internal reviewer/stage emails still do. Saving refuses a text that drops a placeholder carrying the order number, link or amount (every default placeholder except `:site`/`:service`), or invents one; a text equal to its default is not stored. **VAT on the commission** is a setting (`vat.on_commission`, off by default, a tax question for the accountant): when on, `service_orders.vat_on_commission` is snapshotted at creation, shrinks with refunds like the commission, and is part of "due to us" (never of the customer's total); the report tables then show a "Commission + VAT" column via `IncomeStatement::commissionWithVat()`. Result documents can be replaced or deleted from the order page (`OrderDocumentService`, which only ever deletes inside that order's own folder).

**Not built yet:** automatic refunds through the gateways' APIs. Thawani's refund docs (a JavaScript Stoplight site) could not be read, and the one secondary source says Thawani refunds full payments only, while every refund here is partial (the fee is never refunded), so do not build it from guesses; refunds stay recorded manually. **Unverified against the real services:** Thawani's session `total_amount` is compared to the order total in baisa when present (a different unit would refuse every payment as `amount_mismatch`; check the first sandbox run's gateway log); NBO/CCAvenue are ports and untested live; Tamimah as above.

### The form-builder fork (`packages/packstub/filament-form-builder`)

An in-repo, permanently customized fork (bilingual fields, file upload field, site styling; see its `CHANGELOG.md`, which every change should extend). It depends on `App\Support\Localized`. Generic hooks the app uses, all on the `FormBuilder` facade: `registerFormTab`, `closedWhen`, `beforeForm`, `holdNotificationsWhen`, plus `SubmissionReceived::redirectTo()`. Uploads go to a **private** disk (`local`) and are reached only through a signed `form-files/{token}` route that checks the `viewAny` gate on the form model; the app's published `config/packstub-form-builder.php` must stay in step with the package's.

- The form editor (in the fork): name/slug first, fields folded to label/required/width with "More options", a grouped "Add field" menu, typed defaults, "Paste a list" for choices, a Preview slide-over (`form-preview/{token}`, cached draft, sandboxed iframe), "Start from a template" on new forms, an All/EN/AR switch, and **conditional fields** ("Show this field only when", one rule on an earlier field; `Support\FieldConditions` on the server decides, hidden fields are stored as null). The "Service & payment" tab never offers a conditional field as the customer's name/phone/email (`FormOrderSettings::fieldOptions()`): a hidden one would leave the order without it.

### Form insights and charts

- `Services\Forms\FormInsights` counts a form's submissions in PHP over the stored JSON (no MySQL JSON functions, so sqlite tests work): per day, and per chartable field (`CHARTABLE`: select, radio, conditional_radio, checkboxes, checkbox, nationality, number, date; free text/email/phone/file never). Counts are cached by stored value under a stamp (submission count/max id/max updated_at), labels applied afterwards in the current locale. Nationalities are stored as the visitor's-language name, so both spellings fold to `code:OM` through `Country`. Paid forms: `ordersByStatus()` and `income()` (an `IncomeStatement` with the new `formId`, so the money matches the Income report).
- `Services\Forms\FormChart` turns results into a spec for `resources/js/form-charts.js` (Chart.js; a separate Vite entry) via `<x-form-insights.chart>` (canvas + a `<details>` table twin). Forms: one-colour horizontal bar in the form's choice order; donut only on request, one-answer fields, ≤ 6 slices; tick box = meter; numbers/dates/timeline = columns; nationality = map (chartjs-chart-geo + world-atlas 1:50m, lazy chunk) plus a top-10 bar. Colours are the dataviz reference palette, light and dark.
- Admin: `Filament\Forms\ViewFormInsights` (`/admin/forms/{id}/insights`), added to the package resource through `FormBuilder::registerResourcePage()` **in `AppServiceProvider::register()`** (Filament loads panel routes while package providers boot, before the app's `boot()`), plus `registerRecordAction()` for the list/editor button. Access = `view` on the form; the money section also needs the Income report permission. PDF/CSV: `FormInsightsExport`.
- Submissions: their own page `/admin/forms/{id}/submissions` (the package's `ManageSubmissions`), one of a form's tabs (edit / submissions / insights); clicking a form in the list opens it. Its actions are grouped (an Export menu, a ⋮ menu per row, the bulk menu); the app adds a PDF per language (all as filtered, selected, one) into them via `FormBuilder::registerSubmissionActions()` → `Filament\Forms\SubmissionPdfActions` → `Services\Forms\SubmissionsPdf` (a question/answer block per submission through `ExportPdf`/`pdf/export`, capped at `MAX_SUBMISSIONS`; files by name, never a signed link).
- Public: CMS block `form_chart` (`Support\FormChartBlock`): never a form linked to a paid service, nothing shown under 5 answers (admins can only raise it), answers given by fewer than 3 people folded into "Other".

### Racing database integration (`/racing/*`)

An external, HTTP-only ColdFusion racing site is scraped server-side and re-presented in our layout. Nothing is stored in our DB; everything is cached.

- `app/Services/Racing/`: `RacingClient` (HTTP + cache, the only thing that talks to the source), plus parsers (`RacingParser` search/profile, `RacingMeetingParser` race-day pages, `RacingHandicapParser` JSON grid, `RacingCalendarParser`), `RacingPdf` (mPDF), `RacingUnavailableException` for source outages. Config and TTLs are in `config/racing.php` (`RACING_*` env vars).
- Controllers `Racing*Controller`, views in `resources/views/site/racing/` and `components/racing/`, PDF views in `resources/views/pdf/racing/`, helpers `Support\RacingLinks`, `RacingSeo`, `PdfText`. Three CMS blocks embed it: `horse_search`, `race_calendar`, `race_widget` (the widget has a no-reload JS enhancement in `resources/js/race-widget.js` that falls back to plain links).
- Upstream hazards that are not obvious from the code:
  - Never send an unvetted race id to the meeting "shell" pages. An unknown id returns a 3–10 MB page in 25–60+ s. Validate first with the cheap `race.cfc?method=getRaceLink`/`raceInfo` call, as the existing controllers do.
  - Never send a malformed `dateFrom`/`dateTo` to the race-dates endpoint; it returns every race ever (~11 s). Only dates derived from a validated season are sent.
  - Search is Latin-only and the source keeps language in a session, so `lang` is sent explicitly on every call.
  - The source's "Local"/"Non-Local" handicap labels look inverted; that's upstream.
- PDFs: mPDF with the bundled Cairo font (static cuts in `resources/fonts/cairo/`; mPDF can't use variable fonts — see the README there), black/white/gray only (a test enforces it for racing), QR code to the page URL. Use `PdfText::dir()` around values so Latin-in-Arabic text isn't bidi-flipped. mPDF can't do Tailwind/flex, so PDF views are plain tables.
- Print/PDF/share toolbar (`x-racing.tools`) appears on profile and race pages only.

### Racing silks designer (CMS block `silks_designer`)

A free tool: visitors design jockey silks (body, sleeves, cap: a pattern + main colour + pattern colour each) and download them as PNG or SVG. Nothing is stored; a later paid service or a three.js/Babylon.js renderer can reuse the same design data.

- **The design is the query string** (`?body=hoops&body1=royal-blue&body2=white&sleeves=…&cap=…`, `Support\Silks\SilksDesign`): it is the share link, the no-JS form submission (the block is a GET form) and the image URL. Unknown or switched-off keys fall back to `SilksDesign::DEFAULT`, so old links never break. `plain` is a built-in pattern for every area, never a row.
- **One drawing** (`components/silks/figure.blade.php` + `area`, geometry in `SilksTemplate`): each area has its own local box (`SilksTemplate::BOXES`), its pattern is clipped to its outline, and the sleeve pattern is reused mirrored for both sleeves. The SVG is always `dir="ltr"` (an Arabic page must not swap the sleeves) and must stay well-formed XML (no bare attributes like `data-x`): `/silks/image` serves it standalone, with the description wrapped underneath, and `resources/js/silks-designer.js` turns that same file into the PNG, so both downloads always match.
- **Downloads**: the SVG and PNG carry the General Settings logo on top (`RacingPdf::siteLogo()`, embedded as a data: URI, so the SVG's CSP allows `img-src data:`). The **PDF** (`POST /silks/pdf`, `pdf/silks.blade.php`, in colour) cannot use the SVG: mPDF ignores `clipPath`, so patterns spill out of the jacket. The browser draws `/silks/image?bare=1` (no logo, no caption) to a PNG and posts it with the design; the server only accepts a real PNG of a sane size, builds every text from the design itself, and prints the page link only if it is on our host. In mPDF, a colour swatch must be a one-cell table (a sized `div` in a cell is not painted).
- **Link and QR code**: every download prints a link (and a QR code) that reopens the design: `Support\Silks\SilksLink::for($page, $design)`. `$page` is the designer page's address sent by the browser (`?page=` on `/silks/image`, a field on the PDF post), used only when its host is ours, rebuilt as page + `lang` + the short form `?silks=pattern.main.accent~…~…` (`SilksDesign::compact()`, accepted by `fromQuery()`; spelled-out parameters win). Keep it short: mPDF cannot wrap a long unbroken URL in a table cell and shrinks the whole table instead, so the PDF prints it on its own line. The PNG/SVG QR is drawn from `mpdf/qrcode`'s matrix (`SilksLink::qrRects()`, checked module for module against the library's renderer in the tests); the PDF uses mPDF's `<barcode type="QR">`.
- **Admin** (CMS group): `SilkColor` / `SilkPattern` resources, both with "Add missing defaults" (`SilksDefaults`, also what the migration inserts: the 18 standard racing colours, 50 patterns). Pattern markup is admin-typed and printed raw, so it always goes through `SilkSvgSanitizer` (allow list: plain shapes and geometry, `fill`/`stroke` only `currentColor`/`none`; the model mutator cleans it, the form refuses anything it would drop). Pattern elements are painted in the visitor's pattern colour through `currentColor`.
- Descriptions follow the registration style ("Red, white chevrons, dark blue sleeves, red cap, white quarters"): templates in `lang/*/silks.php` (`describe.*`), mirrored in the script's `describe()`. English sleeve/cap pattern names must be nouns ("Hoops", not "Hooped") for that to read right.
- Put the block on a CMS page whose slug does **not** start with `racing` (the `/{slug}` regex reserves that prefix, so `racing-silks` 404s); `design-your-silks` works.

### Stable bookings (owners, slots, public booking, checkout, statements, packages, reviews)

Stable owners register and run their stables; customers book dated slots (riding training first). Built: owner accounts, the `/stable` panel, admin approval with a per-stable commission, services, weekly schedules → slots, closed days, trainers/horses, per-stable booking settings (phase 1); the public booking engine, checkout, the stable's own gateway accounts, booking notifications, cancelling and attendance (phase 2). statements, balances and settlements (phase 3); lesson packages and reviews (phase 4). Admins can work in any stable's panel on its owner's behalf (below).

- **Owners** are `users` with `type = stable_owner` (`User::TYPE_STABLE_OWNER`), linked to stables through `stable_user` (role owner/staff). `User` implements `FilamentUser`: owners may open `/stable` only, everyone else keeps `/admin` as before (`canAccessPanel`). They sign up at `/stable/register` (email + password + phone confirmed by an SMS code, reusing `CustomerOtpService::check()`), and sign in with email/password or phone + code. Codes are strings (`digits:6`), never `numeric()`: a leading 0 would be dropped.
- **The panel** uses Filament tenancy with `Stable` as the tenant (URL slug). Filament scopes each resource model to the tenant with a global scope registered when the panel boots; tests must call `Filament::bootCurrentPanel()` after `setTenant()`, or lists are unscoped. Owners have no Shield permissions: the policies of the stable models (`Policies\Concerns\ChecksStableMembership`) allow a member for their own stable's records, else fall back to Shield.
- **Approval**: a registered stable is `approval_status = pending` (existing admin-created stables default to approved). `Stable::active()` (the public listing) requires approved. `Services\Stables\StableApproval` approves (needs a commission: there is **no global commission**, each stable has `commission_type`/`commission_value` on its row, snapshotted onto bookings later), rejects or suspends with a reason; admins get an email (`StableApprovers`: super admins + `Update:Stable` holders) and a bilingual WhatsApp alert (`stable_registration`) on registration, owners an email + SMS on each decision in their `users.locale`. "Link an owner" gives an existing directory stable to a registered owner.
- **Slots**: `StableSchedule` (weekdays as Carbon numbers 0 = Sunday, start times, optional capacity/trainer, validity) → `Services\Stables\SlotGenerator` → `booking_slots` up to the stable's horizon (`booking_settings.horizon_days`). Rules: started slots are never touched; a slot with bookings is never deleted or rewritten; existing slots are only rewritten when the owner saves that schedule (`refresh: true`), so the nightly `stables:generate-slots` never undoes a change to a single slot; schedule slots can be closed but not deleted (the nightly run would recreate them). Places taken are counted live from `stable_bookings` in a holding status (`StableBookingStatus::holdingValues()`, pending included), never a counter.
- **Time zone**: the app runs in UTC; slot dates/times are the stable's wall clock in `config('stable_bookings.timezone')` (Asia/Muscat). Use `BookingSlot::today()`, `startsAt()`, `hasStarted()`, not `now()`. Dates/times are stored as plain `Y-m-d` / `H:i:s` strings (mutators) so sqlite tests compare like MySQL.
- **Owner settings** (`stables.booking_settings` JSON, read only through `Support\StableBookingSettings`): horizon, online cancellation cutoff hours, payment options (online / at the stable; the fee and commission still apply to pay-at-stable bookings), rider fields with show/required each, waiver text, alert channels, staff on/off (trainers/horses screens).
- Texts: `lang/*/stable_panel.php` (panel, owner mails/SMS, enums), `lang/*/admin_stable.php` (admin). Tests: `tests/Concerns/PreparesStableBookings` (portable tables + helpers). The Livewire captcha draws a new code each render: tests set `filament-captcha.charset` to one letter.
- **A booking is a `ServiceOrder` + a `stable_bookings` row** (`Services\Stables\CreateStableBooking`, slot row locked while places are counted). The order has no `service_id`/`form_id`; it has `stable_id`, `collected_by` (`platform` | `stable`) and `stable_payment_account_id`. Use `ServiceOrder::serviceName()` (never `$order->service?->…`) to name any order. Money: price = per-rider price × riders, the **site-wide** fee rule (`ServiceFeeSetting::resolveGlobal()`), VAT as usual, the stable's commission snapshotted in the order's commission columns (`StableBookingPricing`). Online → `pending_payment` (the booking holds its places; `orders:expire-pending` cancels both through `OrderPaymentService::cancelPending()` → `StableBookingActions::orderCancelled()`); pay at the stable → order `new` + `payment_status = on_site` (`PaymentStatus::OnSite`), confirmed at once; free → confirmed at once.
- **Lifecycle** in `Services\Stables\StableBookingActions` only: `confirm()` (listener `ConfirmStableBookingOnPayment` on `ServiceOrderReceived`; a late payment revives an expired booking even past capacity and notes it on the order), customer cancel within the stable's `cancellation_hours`, stable cancel with a reason, attended / no-show (these complete the order). A cancelled paid booking leaves the order cancelled + paid, i.e. `refundDue()`; refunds are recorded as for any order (the stable refunds its own `collected_by = stable` money).
- **Notifications**: bookings never use the generic order messages (`NotifyOnOrderReceived` skips them). `StableBookingConfirmed`/`StableBookingCancelled` → `SendStableBookingNotifications` → one `Jobs\SendStableBookingNotification` per audience/channel: the customer by SMS (+ email), the stable by its chosen channels (WhatsApp bilingual, only while the site's WhatsApp is on). Texts in `lang/*/stable_bookings.php` (not admin-editable yet).
- **Own gateway accounts** (`StablePaymentAccount`, keys in an `encrypted:array` column; changing keys resets approval): the owner picks "own gateway" + a gateway in Booking settings; keys are tested (`testConnection()` on each gateway), admins approve/reject them in the stable's "Gateway accounts" tab. Until approved we collect. Every gateway reads its keys through `Concerns\UsesPaymentAccount` (`setting()`/`secret()`, else the site's `<gateway>.<key>`); anything that talks to a gateway about an order must use `PaymentGateways::forOrder()` / `findForOrder()` (checkout) or `bind()` (returns, callbacks, webhooks, sweeps). The Thawani webhook finds the order before checking the signature with that order's secret; CCAvenue's callback URL carries `?account=` because the answer can only be decrypted with the stable's key. `IncomeStatement` leaves out `collected_by = stable` orders.
- **Public pages**: `/bookings/search` (date, riders, region, city, time of day; a 7-day strip; next opening when empty), `/bookings/{stable-slug}/{offering}`, `/bookings/slots/{slot}` (the form asks only the rider fields the stable switched on), the booking card on `/orders/{number}` and `/account/orders/{number}` (cancel button for the signed-in customer), a "Book a session here" block on the stable page. `Services\Stables\SlotFinder` decides what is bookable. Blade: never mix one-line `@php(...)` with `@php … @endphp` blocks in one view (Blade mis-compiles it).
- **Statements and balances** (`Services\Reports\StableStatement` + `StableLedgerRow`, baisa like `IncomeStatement`): a row per booking order that carries money: online paid/refunded (dated `paid_at`), and pay-at-the-stable ones only once marked **attended** (dated `attended_at`; unmarked past ones are counted by `unmarkedAtStable()` and flagged). `stableShare = price + VAT on price − refunded − earned commission (+ its VAT)`, `ourShare = fee + VAT on fee + commission (+ VAT)`; held by us (`collected_by = platform`) → we owe the stable its share, else the stable owes us ours. Balance (positive = we owe the stable) = Σ rows − payouts + receipts (`StableSettlement`, recorded by admins through `Services\Stables\StableSettlements`, which tells the owners; `paid_on` stored as plain `Y-m-d`). Owner: dashboard `StableFinanceOverview` + `TodayBookingsWidget`, the Statement page, commission and share columns on Bookings. Admin: Payments → "Stable balances" (`StableBalances`, record payout / payment received), `StableStatementReport` (hidden page, `?stable=`), the stable's Settlements tab. PDF/CSV: `StableStatementExport`, `pdf/stable-statement.blade.php` (landscape). New admin pages use `HasPageShield`: run `shield:generate --all --panel=admin --ignore-existing-policies` or only super admins see them.
- **Lesson packages** (`StablePackage` → a customer's `StablePackagePurchase`, `Services\Stables\StablePackages`): bought by a **signed-in** customer at `/account/packages/buy/{package}` (under `/account/*` so the guest redirect goes to the phone sign-in), paid as a `ServiceOrder` with the same fee/VAT/commission and collection rules as a booking (so it is income in statements); `ActivateStablePackageOnPayment` switches it on (`expires_at = paid + validity_days`), the expiry sweep cancels an unpaid one. A booking paid with a package (`payment_option = package`, `stable_package_purchase_id`) has a free order (no money of its own) and is only allowed for the purchase's own customer, service, validity and sessions left (row-locked in `CreateStableBooking::lockPackage()`). Sessions used are counted live from the holding bookings, so a cancelled one gives its session back. `ServiceOrder::isStableBooking()` is true for package orders too (it means "a stable's order"); use `stableBooking` / `packagePurchase` to tell them apart.
- **Reviews** (`StableReview`, `Services\Stables\StableReviews`): one per booking, only by its customer, only once the stable marked it attended, within 60 days; marking attended sends an SMS invite (`SendStableBookingNotification::REVIEW_INVITE`) to the account order page (`#review`). Published at once with the author as "First L."; the owner replies from `/stable` (Reviews), admins hide/show in the stable's Reviews tab. `Stable::rating()` averages visible reviews; `<x-stars>` renders them.
- **Admins in the owner panel**: `User::managesStables()` (super admin, or Shield `Update:Stable`; never a stable owner) may open `/stable/{slug}` for **any** stable ("Open stable panel" on the admin stable page/list). `getTenants()` then returns every stable (the tenant menu is searchable) and `ChecksStableMembership` treats them as a member **only inside the stable panel and only for the open stable**; everywhere else they keep their Shield permissions. They cannot register stables there (`RegisterStable::canView()`). A warning strip (`filament.stable.admin-banner`, `BODY_START` hook) shows on every page, and `LogAdminStableAccess` (tenant middleware) logs the visit once per session.
- **Change log**: stable models use `Models\Concerns\LogsStableActivity` (spatie activitylog, log name `stable`, `properties.stable_id` + `properties.as_admin`); each model lists what it logs in `stableActivityAttributes()` (never gateway keys); slots, bookings and reviews log updates only, and `SlotGenerator::sync()` runs under `activity()->withoutLogs()`, so a schedule save is one line, not hundreds. Bulk changes must go through models (a query `update()` is not logged). Shown on the admin stable page (`StableChangeLogWidget`) and to the owner (`/stable` → Change log), both via `Filament\Support\StableChangeLogTable`. Tests that switch users within one test must `flushSession()` (Filament's `AuthenticateSession` signs the session out).
- **Insights** (`Services\Reports\StableInsights`, one stable or all when `$stable` is null): money from the same ledger rows as statements (so the numbers always agree), bucketed by day/week/month by the period's length, against the previous period of equal length (`delta()`); occupancy by weekday × start hour over sessions already held (open slots only); top services/packages; new vs returning customers (by phone); cancel rate (expired checkouts excluded) and no-show rate; ratings. Shown on two Filament dashboards with page filters (`HasFiltersForm`): owner `/stable/{slug}/insights`, admin Payments → "Stable insights" (stable filter, stables ranking, CSV), plus `StableBookingsOverview` on the admin dashboard. Widgets live in `app/Filament/Insights` (`$isDiscovered = false`, `ResolvesInsights` picks the stable from the tenant or the filter). Chart colours are the dataviz reference palette slots 1–2 (validated, light and dark via scriptable Chart.js options); the heat grid is the one-hue blue ramp with the percentage in every cell.
- **Reminders**: `stables:send-reminders` (hourly) SMSes confirmed bookings starting within 24 h (and more than 2 h away) whose confirmation is at least 12 h old, once (`stable_bookings.reminded_at`), unless the stable switched `send_reminders` off.


### WhatsApp admin alerts

`wallacemartinss/filament-whatsapp-conector` (Evolution API v2; the "WhatsApp" admin group: instances connected by QR, message history, webhook log; credentials `EVOLUTION_*` in `.env`, webhook `POST /api/webhooks/evolution`). A visitor's new post (transfer board, horses/tools for sale, farriers, from the site controllers or the `/transportation` panel, **not** admin-created records) fires `Events\PublicPostSubmitted` → `Listeners\SendNewPostWhatsAppAlert` → one queued `Jobs\SendWhatsAppMessage` per admin number → `Services\WhatsApp\WhatsAppNotifier` (logs to `notification_logs`, channel `whatsapp`). Configured in General Settings → WhatsApp (`Support\WhatsAppSettings`: switch, instance UUID, numbers, per-type toggles, test button). **Every WhatsApp message is bilingual, English then Arabic** (`BilingualMessage`); never send through the plugin's facade/`WhatsappService` (it prefixes Brazil's `55` to 11-digit numbers, i.e. every Omani one). The `whatsapp-notifications` skill has the rules and the recipe for adding alerts (orders, bookings…). `bootstrap/cache/events.php` exists locally: run `php artisan event:cache` after adding a listener.

### Media Library (`ardavan/filament-file-explorer`)

`MediaLibraryResource` → each library has a root folder (`folder_id`) in the plugin's Finder-style explorer; files are Spatie media on the **public** disk, so each has a public link (`APP_URL/storage/{id}/{file}`). **Never edit the plugin or publish its views**: extend it. `App\Livewire\MediaExplorer` (Livewire name `media-explorer`, used by `ManageMediaLibraryFiles`' own page view) subclasses the plugin component; its view `@include`s the plugin's view unchanged and adds the share bar (`filament/media-library/share-bar`: copy link, share sheet with WhatsApp/email/native share, QR via `qrSvg()`). It also replaces the plugin's hardcoded Persian upload toast (the plugin's `updatedFiles()` body cannot be translated) with a translated one offering "Copy link". The files table adds its link column/actions in `ListMediaLibraryFiles::table()` via the public Table API. Links come only from `Support\MediaLinks` (null for a non-public disk). Access: `Support\MediaLibraryAuthorizer` (set in `config/filament-file-explorer.php`) maps the plugin's abilities to the `MediaLibrary` policy (view → browse/download, update → upload/rename/move/delete files) and refuses folders of no library; it also guards the plugin's `/file-explorer/media/*` routes. Deleting a library deletes its folders and files (confirmation shows the count); the root folder carries `en_name` and follows renames. `app/Providers/FilamentFileExplorerServiceProvider.php` replaces the plugin's provider (`dont-discover`) because its `packageBooted()` calls a Livewire 4-only method: recheck it after a plugin update. Tests: `tests/Concerns/MakesMediaLibraries`.

### Other conventions worth knowing

- **Currency display is never a hardcoded `"OMR"` string.** General Settings has a `currency_code`/`currency_symbol` pair plus an optional `currency_icon` (SVG, disk `public`, directory `branding`, same upload pattern as `site_logo`/`app_logo`/`favicon`). Read it through `SiteSetting::currency()` (`['code','symbol','icon_url']`) or `SiteSetting::formatCurrency()`, and render it with the `<x-currency-symbol>` component, which shows the uploaded SVG icon when `currency_icon` is set and falls back to the plain `currency_symbol` text when it isn't. Any new blade view, widget, or PDF that displays a money amount must use this component (or `SiteSetting::currency()`) instead of printing `OMR`/a bare symbol, so it picks up an admin's currency icon upload automatically. The `CURRENCY`/`'OMR'` constants inside the payment gateway classes (`CcAvenueGateway`, `NboGateway`) are wire-format codes for those APIs, not display text, and are exempt.
- **Every new or reworked public page gets visuals, not just text.** Use Heroicons (`<x-heroicon-o-…>`, from `blade-ui-kit/blade-heroicons`, already installed through Filament; `<x-dynamic-component :component="…">` when the name is computed) on every action button (download, pay, print, back, …) and on section headings, show statuses as cards/badges with an icon tinted by the enum's `color()` (success = emerald, info = sky, warning = amber, danger = red, gray = warm), and give lists/timelines icon markers instead of plain lines. Icons are decorative (`aria-hidden="true"`), the text label always stays. Directional icons (arrows, chevrons) need `rtl:rotate-180`. Write full literal Tailwind class names (no string-built `bg-{$tone}-50`) so the build finds them, and run `npm run build`. The order pages' `site/orders/_status-cards` and `_timeline` partials are the reference. PDFs stay black/white/gray tables (mPDF).
- **Every admin List/View page has "PDF" and "CSV" export buttons** (one item per language in `config/languages.php`) from the `App\Filament\Concerns\HasExportActions` trait: a new `ListRecords`/`ViewRecord` page only needs `use HasExportActions;` (Filament calls `cacheHasExportActions()` itself, so `getHeaderActions()` stays untouched). The list export is the table as filtered/searched/sorted with its visible columns; the view export walks the page's infolist (or form) section by section. Both are rebuilt inside the chosen locale, so labels come out in that language only if they are `__()` strings. Code in `app/Services/Exports/` (`ExportValue` turns a column/field/entry into plain text), PDF view `pdf/export.blade.php` (site logo, landscape past 6 columns, capped at `ExportPdf::MAX_ROWS`; the CSV has every row).
- **Order timeline text** comes from `OrderEvent::label()`, never `$event->message`: the message is saved in the language of whoever caused the event (usually an admin's English), while `label()` re-translates every type that has an `orders.events.*` string into the viewer's language.
- `AppServiceProvider` globally hooks every Filament `FileUpload` and Spatie media upload into `Support\ImageCompressor`, so images are compressed automatically, and wires the form-builder hooks above.
- Posting forms on the public site (transfer-board, horses-for-sale, farriers, tools-for-sale) are guarded by `marcogermani87/filament-captcha` via a `/…/captcha` route each; posts expire via the scheduled commands above.
- Vite entry points (`vite.config.js`): `app.{css,js}`, `site.{css,js}` (public site), and `css/filament/admin/theme.css` (admin theme).
- `routes/api.php` is essentially empty; the API is generated by `rupadana/filament-api-service`.
